### 今日完成

- 重构为 7 个文件，最大一个 88 行：

```

    ├── session.py       对话上下文状态（状态层）
    ├── terminal.py      终端显示工具（CLI 展示层）
    └── repl.py          CLI 交互循环（CLI 展示层）
```

- 顺手修掉上一轮引入的一个格式问题：`sanitize_for_terminal` 当时插在了常量中间，把 `DEFAULT_HOST` 和 `DEFAULT_MODEL` 劈成两段，函数与常量之间还漏了空行。现在默认值全部收进 `config.py`

### 设计取舍
- **拆分的依据是依赖方向，不是代码行数**：`client`（通信）和 `session`（状态）都不引用任何终端相关的代码，所以做 Web 时后端可以直接复用这两个模块，只需要另写一套展示层。`terminal` 和 `repl` 是 CLI 专属的，做 Web 时整体换掉即可
- **`client.chat_stream()` 产出的是模型原文，不做任何渲染处理**：终端转义序列的过滤移到了 `terminal.sanitize()`，由展示层在渲染时调用。这样「取数据」和「怎么显示」是分开的——如果输出目标从终端换成浏览器，过滤规则可以完全不一样，而核心代码一行都不用改
- **没有拆得更细**：没有给参数解析单开模块，也没有搞插件式的展示层抽象。当前这个规模还用不上，过度设计只会让代码更难读

### 设计取舍
- **共享包的边界怎么划**：`shared/llm_chat` 只放「调模型」和「存上下文」，不放任何终端或浏览器相关的东西。CLI 的转义序列过滤、Web 的 SSE 报文编码，都留在各自的展示层。这样以后再加第三种形态（比如桌面端），共享层一行都不用动
- **前端怎么做到「只订阅」**：后端推送的是结构化事件（delta / error / done），前端只做 `JSON.parse` 然后把文本追加到气泡里。前端不知道模型是什么、历史有多长、为什么会失败——它只负责把收到的东西画出来
- **为什么用 POST + fetch 读流，而不是 EventSource**：EventSource 只支持 GET，长消息得拼进 URL，很快就撞上长度限制。改成 fetch + `ReadableStream` 手动切分 SSE 报文，既支持长输入，代码也只多了十几行
- **默认只监听 127.0.0.1**：这个服务没有鉴权，绑到 `0.0.0.0` 等于把本机的模型算力开放给整个局域网。`--bind` 参数保留了这个能力，但传非本机地址时会打印提醒
- **前端不用构建工具**：单个 HTML 文件 + 原生 JS，没有 npm、没有打包步骤。少一层工具链，别人 clone 下来就能跑

- Part 1 回归：`--help` 与完整对话流程退出码均为 0，从仓库根目录运行也正常
- Part 2 接口：`/api/health` 正常返回模型列表；`/` 返回前端页面（200、text/html）；`/api/chat` 逐块推送 delta 并以 done 收尾

### 设计取舍
- **Markdown 自己写，不引 marked.js**：引第三方库意味着页面依赖 CDN，断网或离线时格式全丢。这个项目一直保持「clone 下来就能跑」，这条不能破。代价是语法支持有限，够用即可
- **先转义、再套格式**：这是必须的顺序。模型输出属于不可信内容，如果先套格式再处理，模型返回的 `<script>` 会被浏览器当成真标签执行。现在所有文本先过 `escapeHtml`，后续替换只生成我们自己写死的受控标签，输出里不可能出现模型自带的标签
- **不支持 `_斜体_`**：下划线在代码和变量名里太常见（`snake_case_name`），认成斜体反而会破坏内容。这是在「支持更多语法」和「不误伤内容」之间做的取舍
- **主题在 `<head>` 里用内联脚本决定**：外链脚本要等下载完才执行，那时首帧已经画出来了，切换主题时能看到明显闪白。内联脚本在首次绘制前就把 `data-theme` 设好
- **流式渲染用 requestAnimationFrame 合并**：每来一个增量本来都要重渲染整段已收到的文本，不合并的话长回复会掉帧
- **自动滚动只在用户已经贴着底部时才做**：否则用户往上翻看历史时，会被新内容不停地拽回底部

### 验证情况
- 渲染器单独用 Node 跑了 19 个用例并全部通过。其中 4 个是安全场景：`<script>` 标签、`<img onerror>`、引号转义、代码块内的 HTML，都确认被正确转义；另有 `javascript:` 链接被拒绝的用例
- 静态资源：四个文件都返回 200，MIME 类型正确（ES module 对 JS 的 MIME 有要求）
- 接口与 SSE 复测正常，模型输出含代码块时的推送也正常
- 两个 JS 文件通过 `node --check` 语法检查

### 目前的想法
- 前端拆成四个文件之后，`app.js` 里只剩「组织 UI + 订阅事件」两件事，`markdown.js` 成了纯函数，可以直接用 Node 跑测试。这比全塞在一个 HTML 里好维护得多——渲染逻辑的正确性能脱离浏览器单独验证

- **PyTorch 安装拆成两步，并且不写进 `requirements.txt`**：torch 必须从 PyTorch 官方源装 CUDA 版本，走默认的 PyPI 会装成 CPU 版，而那种版本的表现是「能 import、`is_available()` 返回 True、一算就报 no kernel image」。把它单独拎出来并配一句说明，比放进 requirements 里"看着像一键安装"要安全
- **数据集的 yaml 自己生成，不用 ultralytics 内置的那份**：内置配置里的 `path` 是相对路径，数据集会被下载到 ultralytics 的全局设置目录，位置不由项目控制。自己生成一份指向项目目录的配置，数据集放哪就完全确定了
- **下载逻辑做成「体积校验 + 断点续传 + 多源重试」**：本机到 GitHub 的连接不稳定，下载中途断掉是常态。这里有个容易踩的点——**传输中断时 HTTP 状态码同样是 200**，只看状态码会把半截文件当成功（这次就中招两次：coco128 下到一半被重置、yolo11n.pt 只下到 72%）。所以完整性校验必须按文件体积来
- **默认关掉 ultralytics 的匿名数据上报**：它默认会把运行环境统计发回官方，与项目无关

- 训练：50 轮跑完，precision 0.858 / recall 0.764 / mAP50 0.846 / mAP50-95 0.673
- 推理：单图检测结果经可视化确认为正确；预热后 640 尺寸 6.6ms/张（152 FPS），480 为 224 FPS，320 为 305 FPS
- 冷启动首帧 3.9 秒，属于 CUDA 初始化与底层算法选型的一次性开销，之后进入稳定帧率

- 一开始把 `predict` 报出的 21 FPS 当成了模型的真实性能，单独测才发现那是**冷启动开销被摊到 128 张图上**的结果，预热后的真实吞吐是 152 FPS。**测量范围没交代清楚，数字就会误导人**——这条比数字本身更值得记下来

- **`/api/detect` 刻意写成同步函数**：GPU 推理是阻塞调用，写成 `async def` 会卡住整个事件循环（连对话的 SSE 推送都会受影响）。现在这个写法下 FastAPI 会把它丢进线程池，两类请求互不干扰
- **检测框用百分比定位的 div，不用 canvas**：坐标换算成百分比后，图片缩放时框会自动跟随；标签就是 HTML，样式好控制。canvas 只有在需要画不规则形状时才值得引入
- **检测失败只降级，不阻断**：没装 ultralytics、没有训练权重、显存不够，都不影响对话功能，只是检测接口返回明确的错误。对话是主功能，不该被可选能力拉下水

- **叙事与裁决必须分开**：一次行动拆成两步——模型先只描写行动过程并判断要不要检定（此时它不知道结果），程序掷骰，再把结果喂回去让它写结局。如果让它一次生成全过程，它会直接编一个成功或失败的结果，骰子就形同虚设
- **规则刻意压到最简**：只保留四属性 + d20 检定这一层骨架。本地跑的是 8B 模型，规则越复杂它越容易记错算错；把复杂度压下去，它才能把精力放在叙事上

- **摘要的时机和范围由程序控制**：什么时候触发压缩、覆盖哪些回合都不是模型说了算，只有摘要正文交给它写

### 设计取舍
- **存档文件名只取最后一段再校验**：文件名来自前端，必须防路径穿越。现在 `../../../windows/win.ini` 这类输入会被挡在 400，而不是真的去读系统文件

- **空分组自动隐藏**：状态和关系不是每局都会出现，留着空标题只会让边栏显得啰嗦

### 卡点与解决
- **存档会悄悄丢数据**：`GameState.to_dict()` 里的角色信息原来是一串手写字段，这一轮给角色加了 `title` / `statuses` / `relations` 之后忘了同步，于是存出去的 JSON 里根本没有这三个字段——而且读回来不报错，只是静默变回默认值。改成用 `dataclasses.asdict()` 递归序列化，以后再加字段也不可能漏
- 这个问题是靠一条「存档往返一致」的断言抓出来的。没有那条断言，它多半会一直潜伏到某次真丢了存档才被发现

### 验证情况
- 状态机制：伤害夹取、回血上限、同名状态刷新而非叠加、`turns=0` 视为长期状态、畸形变更不崩溃
- 状态推进：有限状态每轮递减、`turns=1` 的立即消退、长期状态不受影响
- 存档往返：称号、开场、状态、关系全部保留（修复前这四项里有三项会丢）
- 接口层：读档 / 重新存档 / 删除都走通；路径穿越被拒绝；删除不存在的存档返回 404
- 向后兼容：改动前存的两份旧存档仍能正常读取（缺失字段走默认值）

### 目前的想法
- 这次踩的坑挺有代表性：**序列化代码和数据结构脱节时，错误是静默的**。类型检查帮不上忙，运行时也不报错，只有断言能发现。以后凡是加字段，都该顺手补一条往返断言
- 边栏里每一项都由程序维护这条原则，现在看是对的——正因为如此，才敢把「状态还剩几回合」这种东西直接摆给玩家看

- 内置三个预置世界，替换掉原来那串只有名字的「剧本」选项
- 开局界面支持三种来源：选预置、自己写、给关键词让 GM 生成（可反复重新生成）
- 世界观整段进 GM 提示词，成为叙事底色

### 设计取舍
- **预置世界必须埋冲突，而不是写风景**：三个预置都落在一个具体的谜团上——磨坊停了十年却还在响、灯塔沉了一半看守人仍每天点灯、驿站收的价钱是「一段你自己都不记得的往事」。冒险得有个起点，否则 GM 和玩家会一起站在原地找事做
- **三种来源最后收敛成同一个值**：`worlds.to_world` 统一处理 World 对象、字典、预置世界的名字和空值。调用方可能从 HTTP 请求、存档文件或测试脚本进来，各有各的形态；与其在每个入口写一遍判断，不如只留一个地方
- **`scenario` 保留为 `world.name` 的别名**：旧存档和前端一直在用它。与其做一次大迁移，不如让它变成一个只读的投影——数据的真实来源只有一处
- **「剧本」这个概念被世界观吸收掉**：原来的 SCENARIOS 只是一串名字、没有内容，GM 从里面拿不到任何设定。世界观是它的超集，直接替换更干净

### 卡点与解决
- **接口声明与实现不一致**：`world` 字段声明成 `dict | None`，但实现里支持传预置世界的名字（字符串）——Pydantic 在校验阶段就把字符串拦下了，实现那一支根本没机会跑。是「三种形态都要能用」这条断言逼着两边对齐的
- **`GameState.new` 收到字典会静默通过、直到序列化才炸**：dataclass 不校验字段类型，于是错误被推迟到了 `to_dict` 里才爆出来。修法是让 `to_world` 在入口就完成归一化，而不是等到使用的时候

### 验证情况
- 三种来源全部走通：传世界名、传完整内容、不传（用默认预置）
- AI 生成：给「蒸汽朋克 + 侦探 + 孤岛」，产出《雾港孤岛》，基调悬疑，三个关键词都被揉进了设定（齿轮与蒸汽管道、被流放的侦探、黑塔的禁忌）
- 世界观确实进入 GM 上下文（`build_context` 的第一段就是它）
- 存档往返保留世界名、基调与设定全文
- 旧存档兼容：只有 `scenario` 的老存档会被补成一个最小 World，来源标记为 legacy

### 目前的想法
- 这一轮真正值得记的不是功能，而是两个「静默」问题：类型声明与实现不一致、dataclass 不校验类型。共同点是**错误不在出错的地方报出来**，而是被推迟到很远的地方。两次的修法也是同一个思路——把归一化收口到一个入口
- 「预置内容也要有张力」这条在写的时候花的时间最多，但它决定了玩家进游戏后有没有事可做。三个里我最满意驿站那条：它把「代价」具象成了可以交易的东西

## 2026-10-05（第十六轮：流式输出与容错）

### 今日完成
- 回合接口改成 SSE 流式：实测第一个字 1 秒左右出现，整轮三十秒上下
- 新增 `jsonstream.py`：在不完整的 JSON 里提取字段值，让 JSON 模式也能边生成边显示
- 生成中可中断：点「停止」断开连接，后端把这一轮已写进角色卡的改动退回快照
- 补上三层容错：解析失败降级用叙事、什么都没收到就退回非流式重试、任何意外都转成 `error` 事件
- 非流式的 `play()` 改成流式事件的消费者，避免两条路径分叉

### 设计取舍
- **JSON 模式下做流式，靠的是「边收边猜」**：模型吐的是半个 JSON，没法 `json.loads`。新增的 `jsonstream` 只做一件事——找到 `"narration": "` 之后的内容并处理转义，遇到没收全的转义序列就先跳过。它不理解 JSON 结构，因此也不怕模型在字段之间插空白
- **检定后的第二段叙事改成「追加」而不是「替换」**：一开始是替换，结果玩家会看到刚逐字读完的文字当面消失，观感很差。改成追加后需要在两段之间补一个空行——前端按空行分段，后端存的也是两段拼接的结果，两边显示才对得上
- **中断必须回滚**：前端断开时，这一轮的伤害和物品已经写进角色卡了，但回合还没提交。用一份角色卡快照把它退回去，避免留下「掉了血却没有这一回合」的脏状态。角色卡很小，每次深拷贝的代价可以忽略
- **`play()` 不再自己实现一遍**：它现在只是把 `play_stream` 的事件消费掉。两条路径各写一遍的话，早晚会在某个分支上分叉——这比多一层间接更危险
- **降级优先于重试**：JSON 坏了但叙事是好的就直接用叙事。玩家已经看着字一个个出来了，这时再报错重来最伤人；只有连叙事都没收到才值得重试

### 卡点与解决
- **连续两次「用了没定义的名字」**：先是 `StreamingResponse` 忘了 import，修完又发现 `_sse` 这个辅助函数是我在 Part 2 里写的、Part 4 根本没有。两次卡在同一个地方，而 `py_compile` 只查语法、不查名字解析，全都没拦住
- 教训很直接：**静态检查通过的代码不等于能跑的代码**。这类错误的发现成本完全取决于有没有真的发一个请求过去——这次是靠每次改完都跑一次冒烟测试才立刻定位，否则要等界面上点一下才发现
- 顺带确认了模型在「踹开上锁的木门」这类行动上仍会**提前写出结果**（直接写「门栓被打破」）。这是 8B 的能力边界，提示词逼不出来，记进已知限制

### 验证情况
- 流式：首个 delta 在 1.09s 到达，整轮 31.6s；事件序列 `phase → delta×N → check → phase → delta×N → changes → done`
- 分段一致性：有检定时两段之间有空行，**流式收到的内容与后端存储的完全一致**
- 中断：收到 3 个事件后断开，回合数没变、HP 被回滚 ✓
- 容错四组用例（用模拟客户端，不依赖真实模型）：两段拼接、单段、JSON 坏但叙事好、什么都没收到触发重试——全部通过
- JSON 提取器 21 项用例通过，含跨 chunk 的转义处理与分片重组

### 目前的想法
- 「静态检查通过 ≠ 能跑」这条，这两次是用最笨的方式学会的：改完不测就往下走，多花了两轮。而冒烟测试的成本其实很低——起个服务、发一个请求而已，但它能抓到类型检查和语法检查都看不见的那类错误
- 流式带来的体验差别比预想的大。三十秒的干等和「一秒后开始出字」在感受上完全是两回事，而这个改动的核心其实只有一个函数：从半个 JSON 里抠字段
