# Part 4 — AI GM 跑团网页

状态：**可玩**

## 这是什么

一个网页跑团游戏：你扮演角色，本地大模型当游戏主持人（GM），负责描述世界、
扮演 NPC、推进剧情；而**骰子和规则由程序来管**。

题材是自创的轻量规则——四属性 + d20 检定。不用 D&D 或 COC 那套完整规则，
原因很直接：本地跑的是 8B 模型，规则越复杂它越容易记错、算错、或者干脆编一个
结果出来。把规则复杂度压下去，它才能把精力放在叙事上。

## 核心设计：叙事与裁决分离

这是整个作品的关键。一次玩家行动会走两步：

```
玩家：我用肩膀撞开那扇腐朽的木门
  ↓
第一步  模型只描写「行动的过程」，并判断要不要检定 —— 此时它还不知道结果
  ↓
第二步  程序掷骰：d20=18 + 体魄调整值 1 = 19 ≥ 难度 12 → 成功
  ↓
第三步  把掷骰结果喂回去，模型写出结局，并「提议」状态变更
  ↓
第四步  状态变更由程序落实：伤害会夹取、回血不超上限、物品不会重复
```

如果让模型一次生成全过程，它会直接编一个成功或失败的结果，骰子就白掷了。
这条分工也是「模型负责叙事、程序负责规则」的具体体现：

| | 负责 | 不负责 |
| --- | --- | --- |
| 模型 | 描写世界、扮演 NPC、判断是否需要检定、提议状态变更 | 不掷骰、不决定成败、不直接改数值 |
| 程序 | 掷骰、判定成败、维护角色数值、管理剧情摘要 | 不编故事 |

## 开局：身份、属性、人设

**身份**决定初始属性的推荐值。内置四个（战士 / 游荡者 / 学者 / 行者），也可以选
**自定义**——自己填身份名、自己分配属性。四条属性总和固定 10 点，每项 1-5；
后端还会再校验一遍，不合法就就近修正。

**人设**是个表单，五个字段全部选填：外貌、性格、目标、来历、特质。

- 勾上「让 GM 补全」：GM 补全空缺、把简略的地方写具体，**玩家已经填好的部分原样保留**；
  它还会**按人设给出属性建议**——一个成天泡在书里的人不该体魄 4
- 不勾：完全按玩家填的执行，GM 一个字都不改，空着就空着
- 生成后可以先看预览，不满意点「重新生成」再来一次。这一轮的属性默认采纳 GM 的建议；
  玩家自己分配过的话以玩家为准

人设会被带进开场叙事和之后的每一次对话——GM 得记得角色是谁，不能写到第三轮就忘。

**特质会在冒险中继续长出来**：当情节确实揭示或改变了角色的性格时，GM 会记下一条新的。

## 规则

- **四属性**：体魄、敏捷、心智、感知，取值 1–5，2 是常人水平
- **调整值** = 属性值 − 2（范围 −1 ~ +3）
- **检定**：d20 + 调整值 ≥ 难度 即成功
- **难度**：容易 8、普通 12、困难 16、极难 20
- **大成功 / 大失败**：d20 掷出 20 必成功，掷出 1 必失败——不管加值多少
- **生命上限** = 10 + 体魄 × 2
- **出身**：战士 / 游荡者 / 学者 / 行者，属性总和都是 10
- **状态效果**：如「扭伤脚踝」，可带剩余回合数。倒计时由程序每回合推进，归零
  自动消失；不带回合数的表示要等剧情解除
- **人际关系**：记录 NPC 对角色的态度，随剧情变化

## 存档

存档放在 `part4-aigm/saves/`，文件名是 `{12位id}-{角色名}.json`，内容是一局的
完整快照（角色、开场叙事、剧情摘要、全部回合记录）。

这个目录被 `.gitignore` 排除，不会被版本控制跟踪。想删就直接删文件，或者在
开局界面点存档条目旁边的「删除」按钮。

## 刷新与恢复

当前对局的 id 存在浏览器 `localStorage` 里，刷新页面会自动接回原来的进度，不用
重新开局。如果服务重启过，内存里的那局已经没了，这时界面会说明原因并回到开局
界面——想跨重启保留进度，请用「存档」。

## 运行

> 必须先激活 conda 环境（与前几个 part 相同）。

```powershell
conda activate ai_project
cd part4-aigm
pip install -r requirements.txt
python src/main.py
```

浏览器打开 <http://127.0.0.1:8100> 。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/health` | 服务与模型状态 |
| `GET` | `/api/options` | 开局选项：身份、剧本、属性规则、人设字段 |
| `POST` | `/api/persona/generate` | 生成或补全人设（不建游戏，供预览与重新生成） |
| `POST` | `/api/game/new` | 开一局，返回开场叙事 |
| `POST` | `/api/game/state` | 取当前进度（刷新页面后用它接回来） |
| `POST` | `/api/game/turn` | 走一个回合 |
| `POST` | `/api/game/save` | 写存档 |
| `GET` | `/api/saves` | 列出存档 |
| `POST` | `/api/game/load` | 读档，恢复一局接着玩 |
| `POST` | `/api/game/delete` | 删除存档 |

    ├── main.py              入口：只做参数解析与模块组装

    │   ├── character.py     角色卡
    │   ├── gamestate.py     一局的状态与存档
    │   ├── prompts.py       GM 的提示词

    └── server/              Web 层

LLM 客户端来自顶层的 `shared/llm_chat`（与 Part 1、Part 2 共用同一份代码）。
为了让 GM 输出结构化指令，`shared/llm_chat/client.py` 新增了一个非流式的
`chat()` 方法，通过 Ollama 的 `format=json` 强制模型输出合法 JSON。

## 长对话怎么处理

跑团是长对话，8B 模型的上下文装不下一整场冒险。所以：

- 最近 8 轮保留原文
- 更早的内容压缩成一段 200 字以内的剧情摘要，逐段向前推进（不重复处理同一段）

摘要由模型生成，但**压缩的时机和范围由程序控制**——什么时候触发、覆盖哪些
回合，都不是模型说了算。

## 已知限制

- 8B 模型偶尔仍会不完全遵守「不提前写出结果」的约束。提示词里用具体例子压制过
  一轮，效果明显，但做不到 100%
- 服务重启后内存里的对局会丢，要保留进度请点「存档」
